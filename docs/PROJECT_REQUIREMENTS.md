# Olist 配送履约与客户满意度分析：项目需求说明书（待确认版）

版本：1.0  
状态：**一期正式确认**。业务、指标、交付、验收、技术环境和语言要求已确认；当前仅进入任务计划确认，未经用户确认不得开始环境迁移、编码、数据库操作、清洗、分析或仪表盘制作。

## 1. 项目背景

本项目在既有 Olist 电商数据分析项目基础上深化，面向模拟电商运营场景，研究订单履约、物流配送和客户满意度之间的关系。项目不预设“配送延迟导致低评分”为结论，而将其及卖家履约、地区物流效率、预计送达准确性等视为待验证的业务假设。

## 2. 项目目标

1. 建立订单配送时效和客户满意度的订单级指标体系。
2. 描述并检验配送延迟与客户评分/低评分率的关联，不将关联表述为因果关系。
3. 识别延迟率或低评分率较高的客户州、商品类别和卖家 ID，并以样本量、差异幅度、效应量和置信区间共同评估业务重要性。
4. 形成可刷新 Power BI 仪表盘、可复现的 SQL/Python 分析流程、处理后的分析数据集和可追溯的书面报告。
5. 提出 3–5 条有数据依据、可落实的运营建议。

## 3. 目标用户与预期动作

| 用户 | 使用场景与预期动作 |
| --- | --- |
| 平台运营人员 | 识别客户体验问题，安排物流优化与运营优先级。 |
| 物流运营人员 | 定位配送效率偏低的客户州和订单类型。 |
| 卖家管理人员 | 按 `seller_id` 筛查延迟率和低评分率异常的卖家，安排履约管理。 |
| 业务管理者 | 通过仪表盘了解履约与满意度概况，并评估改进重点。 |

## 4. 核心业务问题与分析假设

| 编号 | 问题 / 待验证假设 |
| --- | --- |
| BQ-01 | 延迟订单与按时/提前订单的低评分率、平均评分是否存在具有业务意义的差异？ |
| BQ-02 | `delay_days` 增加时，评分分布及低评分率如何变化？ |
| BQ-03 | 哪些客户州的延迟率、配送时长或低评分率较高？ |
| BQ-04 | 哪些商品类别的平均配送时长或延迟率较高？ |
| BQ-05 | 哪些 `seller_id` 的延迟与低评分表现值得优先关注？ |
| BQ-06 | 在地区、品类、卖家、付款与商品属性等可用维度上，哪些因素与低评分有较强且有业务意义的关联？ |

所有发现须使用“与低评分相关”“低评分率明显更高”“可能需要优先关注”等表述；不得使用“导致低评分”“证明因果关系”等表述。

## 5. 数据来源、范围与表关系

### 5.1 数据来源及现状

数据来源为标准 Olist 公开数据集，当前只读取 `data/raw/` 中的原始 CSV，不得修改原始文件。现有 7 张表：客户、订单、订单明细、付款、评价、商品和品类翻译；缺少卖家表和地理表。完整盘点、缺失影响、键匹配与质量结果见 `DATA_INVENTORY.md`、`DATA_QUALITY_REPORT.md`。

### 5.2 一期数据表与关系

| 表 | 粒度 / 主键或候选键 | 主要关系与用途 |
| --- | --- | --- |
| orders | 订单，`order_id` | 样本边界、状态、下单/履约日期、主订单事实。 |
| customers | 客户订单地址，`customer_id` | 通过 `customer_id` 关联订单，提供 `customer_state`。 |
| order_items | 订单明细，`order_id` + `order_item_id` | 通过 `order_id` 关联订单，提供 `product_id`、`seller_id`。 |
| products | 商品，`product_id` | 提供商品类别和属性。 |
| category translation | 品类映射，`product_category_name` | 翻译商品类别；未映射类别须保留标记。 |
| order_reviews | 评价记录 | 通过 `order_id` 关联订单；按 DEC-002 生成订单级主评分。 |
| order_payments | 付款记录，`order_id` + `payment_sequential` | 仅在明确聚合后作为付款特征/分层维度；避免放大订单粒度。 |

### 5.3 一期范围与非范围

一期允许地区到 `customer_state`、卖家到 `seller_id`、商品到商品类别。

一期不包括：卖家所在城市/州推断、客户—卖家配送距离、物流半径、依赖经纬度的精确地图、预测模型、多变量逻辑回归、订单低评分预警模型，以及演示文稿。卖家表为高优先级待补充文件；地理表为二期增强数据。详见 `DECISIONS.md` 的 DEC-004。

## 6. 样本边界与指标定义

| 分析主题 | 纳入规则 | 排除/单列规则 |
| --- | --- | --- |
| 订单总体分析 | 全部订单，按 `order_status` 分别统计 | 不静默删除取消、异常、未签收或未评价订单。 |
| 配送履约分析 | `order_status = delivered`，且实际送达和预计送达日期完整、可解析 | 其他订单单列数量、比例和特征。 |
| 配送与评分关系 | 配送履约样本，且有按 DEC-002 选定的有效订单级评分 | 未评价、无法排序且评分冲突的订单不进入主关系分析，但保留质量统计。 |

`delay_days` 使用日历日期差；`delay_hours_raw` 仅作补充审查。低评分为 1–2 分，中性为 3 分，高评分为 4–5 分。所有字段、分子分母、分类、粒度和敏感性分析要求以 `METRICS.md` 为唯一指标口径来源；已确认决策以 `DECISIONS.md` 为准。

## 7. 数据质量检查要求

1. 保留原始数据不变，清洗前后记录每个关键筛选/处理步骤的行数与原因。
2. 检查文件完整性、字段类型、候选键唯一性、完全重复、关键字段缺失、日期可解析性与日期顺序。
3. 在连接前后检查订单粒度，防止订单明细、付款或多评价导致订单重复放大。
4. 单列未评价订单、取消/异常状态、缺少实际送达日期、缺少品类及未映射品类。
5. 生成 `review_record_count`、`has_multiple_reviews`、`has_conflicting_review_scores`，并执行最新有效评价与最低有效评价的敏感性分析。
6. 对月度趋势标识并排除 2016-09、2016-12、2018-09、2018-10；但保留这些记录在全量统计和边界月份附录中。
7. 异常数据不得静默删除；无法处理的数据必须记录原因、数量、影响和处理方式。

## 9. 分析方法

一期必须包括：

1. 描述性分析：订单状态、履约时长、延迟、评分与未评价情况。
2. 分层比较：按延迟等级、客户州、商品类别、`seller_id` 分层。
3. 相关性分析：使用 Spearman 相关性检查 `delay_days` 与 `review_score` 的关系。
4. 基础统计检验：比较延迟与按时订单低评分率；比较不同延迟等级评分分布；使用卡方检验检查延迟状态与低评分状态的关联。
5. 对适用检验报告效应量和置信区间，不仅报告 p 值；同时审视样本量与差异幅度。
6. 敏感性分析：以同订单最低有效评分替代主评分，比较核心结论是否明显变化。

预测模型、多变量逻辑回归和低评分预警为二期增强方向，不是一期验收条件。

## 13. 验收标准

### 13.1 仪表盘

- 数据模型关系正确，筛选器按时间、客户州、商品类别、卖家 ID、延迟等级正确联动。
- 核心指标与 SQL/Python 结果交叉一致：订单等整数指标必须完全一致；比例指标的显示差异不超过 0.1 个百分点。
- 四个必需页面完整，图表无报错或失效；标题、单位、时间范围、指标定义清晰。
- 明确说明边界月份与数据限制；不展示无数据支持的卖家地区或配送距离指标。
- 可使用 `data/processed/` 中的处理后数据重新刷新。

### 13.2 分析报告

- 包含背景与问题、数据来源与范围、质量和样本筛选、指标、方法、核心发现、检验、地区/品类/卖家结果、3–5 条建议、限制和后续方向。
- 每条核心结论可追溯到指标、表格或图表，并明确区分数据事实、分析推断、业务建议和未验证假设。
- 对相关性和检验结果不做因果表述。

### 13.3 SQL、Python 与数据集

- 原始 `data/raw/` 未被修改，未使用本机绝对路径，能够按照 README 从头运行。
- 文件命名、执行顺序、必要注释和处理前后行数记录清楚。
- 连接前后检验订单粒度；关键指标有 SQL 与 Python 交叉验证。
- 异常数据不被静默删除；无法处理的数据有原因记录。
- 最终可生成供 Power BI 刷新的分析数据集。

## 14. 风险与依赖

| 风险/依赖 | 影响 | 当前应对 |
| --- | --- | --- |
| 缺失卖家表 | 无法验证卖家主数据或做卖家地域分析 | 一期仅按 `seller_id`，建议最终交付前补齐。 |

| 观察性数据 | 容易把相关性误读为因果 | 使用审慎表述，不以预测/因果结论作为一期目标。 |
