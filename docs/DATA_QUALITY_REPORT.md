### 时间边界判定

- 以**下单月**做订单趋势时，2016-09（4 单）、2016-12（1 单）、2018-09（16 单）和 2018-10（4 单）均明显不完整；建议不作为完整月参与环比、同比或月度排名，但应保留在全量订单与履约样本中并在图表注明。
- 不同日期字段代表不同事件；例如 2018-11 的唯一预计送达记录不代表该月有新订单。因此若做“签收月/预计送达月”趋势，也应将各字段首末月标注为观察窗口边界，而不是混用下单月的剔除规则。

## 4. 评价字段检查

- `review_score` 的有效值仅为 1–5，未发现空值或其他无效值。
- 各评分记录数：1 分 11,424；2 分 3,151；3 分 8,179；4 分 19,142；5 分 57,328。
- 99,224 条评价记录对应 98,673 个订单；有 547 个订单存在多条评价，额外评价记录 551 条，单订单最多 3 条评价。
- `review_id` 有 814 条重复键记录，虽无完全重复行。因此在关系分析前，必须确认一单多评的订单级处理规则（例如保留最新创建时间、最低分、平均分，或另建评价记录级分析）；本报告不选择其中任何一种。

现已确认订单级主评分规则：先取最新 `review_answer_timestamp`，再取 `review_creation_date`，最后以 `review_id` 稳定排序；多个有效评价的最低评分只用于后续敏感性分析。本次审查中两个时间字段均无缺失；547 个多评订单中有 202 个评分冲突订单；不存在所有排序字段均完全相同而仍无法决定先后的评价组。因此，按该规则可以形成订单级主评分；若未来增量数据出现无法排序且评分冲突的订单，应标记为冲突并排除在主关系样本之外，而非随意选取记录。

## 7. 延迟字段的可行性与待确认口径

对 `order_estimated_delivery_date` 的时、分、秒进行核验后，99,441 条可解析记录均为 `00:00:00`，无空值或其他时间值。该字段在当前数据中主要表达“预计送达**日期**”，而非精确的预计送达时点。因此主延迟指标已确认使用日历日期差：`DATE(order_delivered_customer_date) - DATE(order_estimated_delivery_date)`，单位为整数天；连续的 `delay_hours_raw` 仅保留作数据审查和补充分析。

下表保留的是确认前、按连续时间差得到的审查结果，用于解释为何不将它作为主分类依据：96,470 个配送履约样本的连续差范围为 -146.0161 至 188.9751 天，且全部含时分秒。

| 当前分类覆盖 | 订单数 | 占配送履约样本 |
| --- | ---: | ---: |
| `delay_days <= 0`（按时或提前） | 88,644 | 91.8876% |
| `0 < delay_days <= 1` | 1,292 | 1.3393% |
| `1 < delay_days <= 3` | 1,370 | 1.4201% |
| `3 < delay_days <= 7` | 1,819 | 1.8856% |
| `delay_days > 7` | 3,345 | 3.4674% |

连续时间差会使 `0 < delay_days <= 1` 的 1,292 单落在原分类空档，并将同一天但晚于午夜签收的订单标为正数。已确认的日历日口径消除了该问题：`delay_days <= 0` 为按时或提前，1–3 天为轻微延迟，4–7 天为中度延迟，超过 7 天为严重延迟。后续实现仍须保留连续 `delay_hours_raw`，不得以它替代主分类字段。

## 9. T08 可复现复核与质量风险（2026-08-06）

本节由 `src/02_validate_raw_data.py` 在 MySQL 只读事务中产生和复核；25 条 SQL 查询与 Python 的 12 组关键指标对账全部通过。完整、非敏感的表盘点和机器可读结果见 `reports/validation/t08_reconciliation_summary.json`，对账范围见 `docs/T08_SQL_PYTHON_RECONCILIATION.md`。

### 9.1 当前数据事实

- 7 份 CSV 与 7 张原始表逐表行数一致；所有已声明外键的孤立键数均为 0。
- `review_score` 无缺失且仅有 1–5；`review_id` 有 789 个重复键组、814 条重复键后续记录。547 个订单有多评价，202 个订单的多评价评分冲突，最多 3 条评价；本任务没有选择或删除任何评价。
- 订单日期顺序异常仅作审计：carrier 早于 purchase 166 单、carrier 早于 approved 1,359 单、客户签收早于 carrier 23 单；approved 早于 purchase、客户签收早于 purchase、预计送达早于 purchase 均为 0。后续清洗规则仍须单独确认。
- 明细金额没有缺失、零值或负值；付款金额无缺失和负值，但有 9 条零付款，分期数范围 0–24，且有 80 个订单的付款序号不连续或不从 1 开始。
- 商品品类缺失 610 条；重量为非正值 4 条，长度/高度/宽度没有非正值。客户 `customer_unique_id` 有 2,997 个重复组，这是跨订单客户标识的预期业务粒度，不是 `customer_id` 主键异常。

### 9.2 订单粒度与样本风险

按订单聚合前，订单可能因明细、付款、评价一对多关系被放大：有多商品订单 9,803 个、多付款订单 2,961 个、多评价订单 547 个，其中 275 个同时有多商品和多付款。若直接内连接三张明细表，当前会产生 117,329 行，而不是天然的一行一个订单。后续订单级分析表必须先分别聚合再连接；T08 未创建该表。

主分析样本漏斗仅用于规模核验：99,441 全部订单 → 96,478 delivered（减少 2,963）→ 96,470 有实际送达日（减少 8）→ 96,470 同时有预计送达日（减少 0）→ 95,824 同时有有效评分（减少 646）。取消订单 625、unavailable 609、非 delivered 2,963、无实际送达日 2,965、无评价订单 768 均被保留，未作永久排除。

### 9.3 不完整月份与待确认事项

四个重点月仍有数据证据支持不纳入主要趋势：2016-09 为 4 单/4 个活跃日（09-04 至 09-15，13.33% 日覆盖），2016-12 为 1 单/1 个活跃日（3.23%），2018-09 为 16 单/11 个活跃日（09-03 至 09-29，36.67%），2018-10 为 4 单/4 个活跃日（10-01 至 10-17，12.90%）。判断基于日期覆盖和首末日期，不只是订单量。
